1. Executive architecture

The artifact is best understood as three layers: the original game logic and MIDP-like APIs, compiled by TeaVM into JavaScript; a small compatibility implementation that emulates the J2ME platform semantics; and an intentionally tiny host bridge that touches actual browser APIs.

2. Runtime model: Java semantics without a JVM

The generated script identifies itself through TeaVM runtime conventions and contains TeaVM’s suspension/resumption machinery for Java threads. Java classes are represented by JavaScript constructor functions and metadata; Java arrays become typed or ordinary JavaScript arrays with wrappers; Java exceptions become JavaScript exceptions; and Java thread blocking points are compiled into resumable state machines.

The important consequence is that the browser does not repeatedly decode JVM opcodes. The expensive semantic translation has already happened at build time. At runtime the game is native JavaScript in the sense that its control flow is JavaScript, but it still follows the Java object model and the MIDP compatibility implementation that was compiled alongside it.

What TeaVM preserves

  • Java class/object behavior and exceptions.
  • Java arrays, strings, integer arithmetic and library calls.
  • Thread/coroutine suspension points, compiled into resumable state machines.
  • The game’s MIDP-facing API shape, implemented by shim classes.

What TeaVM removes

  • No classfile loading or JVM verifier at browser runtime.
  • No bytecode dispatch loop.
  • No actual Java ME handset VM.
  • No native MIDP implementation: the web shim supplies those behaviors.

4. Graphics: MIDP software framebuffer → HTML Canvas

The browser Canvas is not the primary drawing API used by the game. The compiled MIDP graphics implementation maintains an integer pixel buffer and performs fills, blits, text/image compositing, clipping and other operations in software. Presentation is a separate operation.

Allocate the MIDP screen image

Startup creates a 176×208 image/pixel array, clears it, wraps it as the Canvas backing image, and obtains a Graphics-like object for game rendering.

Render entirely into Java-side pixels

The game’s draw routines mutate the backing integer array. The browser DOM does not participate in individual sprites, lines, fonts or fills.

Flush through one bridge call

The Canvas shim calls __present(c.data,w,h). This is the only host-facing operation needed for a complete frame.

Convert packed RGB ordering

__present writes into a Uint32Array overlaying Canvas ImageData. It forces alpha to 255 and byte-swizzles the packed Java pixel value to the native RGBA byte layout expected by the browser buffer.

5. The 3D view: a Wolfenstein-style picture from a Doom-style renderer

Everything in section 4 is about getting pixels out. This section covers how the first-person view gets drawn into the framebuffer in the first place. It isolates the world renderer inside the TeaVM bundle, explains the algorithm in general terms, and then walks through the generated JavaScript.

It is not a raycaster: Doom RPG’s view looks like Wolfenstein 3D: one storey, walls all the same height, flat-coloured floor and ceiling, grid movement, 90° turns. The code doesn’t cast rays, though. Nothing marches a ray through the tile grid column by column. The .bsp levels hold a binary space partition (BSP) of wall line segments. The renderer walks that tree front to back, projects each segment onto the screen, and fills the columns it covers. A Wolf3D raycaster also ends up with exactly one wall per column and a per-column distance, so the output matches. Doom RPG just gets there with Doom’s method.

5.1 The algorithm in brief

A Wolfenstein raycaster answers one question per screen column: what is the nearest wall along this column’s line of sight, and how far away is it? It answers by stepping a ray through the tile map until it hits a solid tile. Wall height on screen is proportional to 1/distance. The distances go into a per-column array, which later clips sprites.

Doom RPG answers the same question in reverse. It doesn’t ask, per column, which wall is there. It asks, per wall, which columns it covers. Because every wall is opaque and full height, the first wall to claim a column owns it completely. If walls arrive nearest-first, every column ends up holding the nearest wall, which is the raycaster’s result. A BSP tree is the classic way to get walls in nearest-first order cheaply, so that is what the level files contain.

5.2 Where it lives in the bundle

TeaVM minifies every identifier, so the renderer has no class name you can grep for. It can be found by following its own debug strings. The game’s profiler overlay prints "nd:%1/%2" (nodes visited), "li:%1/%2/%3" (lines) and "sp:%1/%2/%3" (sprites). The counters it prints are reset at the top of a function that also loads /sintable.bin-derived values. That function is the per-frame entry point, and everything else hangs off it. Strings are referenced as E(n), an index into the pool passed to ZN([...]) at the end of the bundle.

5.3 Level data: a BSP of byte-sized lines

A .bsp file holds a node count followed by 10-byte node records, then a line count followed by 8-byte line records. Coordinates are single bytes multiplied by 8, which gives a 2048 × 2048 unit world in 8-unit steps, or 32 × 32 tiles of 64 units.

// ABm, node records (10 bytes)
e.jB = EB(0); e.im = EB(1);            // bbox xmin, ymin   (EB = (byte & 255) << 3)
e.ij = EB(2); e.hT = EB(3);            // bbox xmax, ymax
e.i4 = EB(5) | (byte4 << 16);          // split coord | axis flags (0x10000 = x, 0x20000 = y, 0 = leaf)
e.hu = De(6) | De(8) << 16;            // two 16-bit children, or (firstLine, lineCount) at a leaf

// line records (8 bytes)
e.g1.gS = EB(0); e.g1.gT = EB(1);      // v1 x, y
e.g0.gS = EB(2); e.g0.gT = EB(3);      // v2 x, y
e.ha = De(4);                          // texture id
e.g4 = De(6) & 65535;                  // flags: 1 two-sided, 2 masked, 128 seen-on-automap, …
// texture u runs 0 → max(|dx|,|dy|) along the line; walls are axis-aligned, so that is its length

Every split is axis-aligned (a vertical or horizontal line through the grid), so choosing a side is one integer comparison, not a dot product. That suits a level built on tiles.

5.4 Walking the frame, in the generated JavaScript

The excerpts below are the beautified bundle. Comments are added and some lines are condensed (a few | 0 coercions and clipping branches elided). Variable names are the bundle’s own unless a comment says otherwise.

Camera setup: SA

SA = (b, c, d) => {                      // b = x, c = y, d = angle (0..255 = full turn)
    J();                                 // static-initialiser guard, see 5.5
    e = Fe.data;                         // 256-entry sine table, 16.16 fixed point
    f = e[d & 255];                      // sin
    d = e[(d + 64 | 0) & 255];           // cos: sin shifted a quarter turn
    b = b - ((16 * d | 0) >> 16) | 0;    // eye sits 16 units behind the player position
    c = c + ((16 * f | 0) >> 16) | 0;
    LA = b; Hb = c;                      // eye x, y
    M9 = d; Mj = -f | 0;  Pd = -(N(b, d) + N(c, Mj) | 0) | 0;   // depth row of the matrix
    Uv = f; Sz = d;       QB = -(N(b, f) + N(c, d) | 0) | 0;   // lateral row
    b = B6; while (--b >= 0) G6.data[b] = 2147483647;          // every column "empty"
    // top half: copy ceiling row Ez into each scanline; bottom half: floor row EV
    ...
    Iw = null; JT(0);                    // BSP walk from the root collects sprites into Iw
    for (i = Iw; i !== null; i = i.hH) T$(i);   // then draw them, far to near
}

BSP traversal: JT

JT = b => {
    c = IX.data[b];
    if (ZU(c)) return;                   // off-screen, or every column it covers is already filled
    b = c.i4;
    if (b & 196608) {                    // 0x30000: an inner node
        d = b & 65535;                   // split coordinate
        if ((b & 131072 && Hb > d) || (b & 65536 && LA > d)) {
            JT(c.hu & 65535); JT(c.hu >> 16 & 65535);    // eye's side first
        } else {
            JT(c.hu >> 16 & 65535); JT(c.hu & 65535);
        }
        return;
    }
    // leaf: copy each line into the scratch segment Ix (transforms are in place), then NR(Ix)
    // and insert each sprite linked to this leaf into Iw, sorted by view depth
}

ZU is what keeps the walk cheap. If the eye is inside the node’s box it always descends. Otherwise it picks the two box corners that form the silhouette as seen from the eye, transforms, clips and projects them like a wall, and then scans G6 across that screen span. If no column there still reads 2147483647, nothing behind the box can show, and the whole subtree is skipped. A Wolf3D raycaster gets this early-out for free when its ray stops. Here it falls out of the column array.

Projecting a segment: JW → V4 → LQ

JW = v => {                              // world → view (both rows of the 2×2 rotation + translation)
    z = N(v.gS, M9) + N(v.gT, Mj) + Pd;  // depth along the view direction
    x = N(v.gS, Uv) + N(v.gT, Sz) + QB;  // lateral offset
    v.gS = z; v.gT = x;
}
// V4: clip against z + x ≥ 0, z − x ≥ 0 (the 90° frustum) and z ≥ 262144 (4.0 in 16.16)
LQ = v => {
    d = BI(Cy(Cu(F(B6), HQ(0, 1)), F(v.gS)));      // scale = width · 2³² / z   (Java long math)
    v.gT = d;                                      // keep 1/z (scaled) for interpolation
    v.gS = Ld + BI(CQ(Cu(F(x), F(d)), 17));        // screen x = centre + x·(width/2)/z
    v.g3 = N(v.g3, d);                             // u · (1/z)
}

A 90° field of view means the focal length is exactly half the view width, which is why the projection has no tangent term.

Filling wall columns: AAP and OE

// AAP: step 1/z (q) and u/z (p) linearly across the screen span n..o
while (n < o) {
    d = (1073741824 / q | 0) << 2;       // back to depth: z ∝ 1/q
    s = Nu(Cu(F(p), F(d))) & 63;         // texture column = (u/z)·z, wrapped to 64
    q = q + g | 0;  p = p + m | 0;
    if (d <= G6.data[n]) {               // nearer than whatever already owns this column
        G6.data[n] = d;
        t = d >> 3;                      // texel step per screen pixel
        l = (64 * q | 0) >> 17;          // on-screen height of a 64-unit wall
        u = Pi - (N(32 - J0, q) >> 17);  // top row: horizon minus (eye height above floor)·scale
        d = (i + s * 64 | 0) << 12;      // texture start (texels stored column-major, 64 per column)
        ... clip u/l to the view, advancing d past rows above the top ...
        OE(n + N(u, B6) | 0, d, t, l);
    }
    n = n + 1 | 0;
}

OE = (b, c, d, e) => {                   // dst index, tex coord (20.12 fixed), step, count
    while (e >= 8) { /* 8 × { px[dst] = pal[texels[c >> 12]]; c += step; dst += width; } */ }
    while (--e >= 0) { Et.data[b] = Hn.data[JS.data[c >> 12]]; c = c + d | 0; b = b + B6 | 0; }
}

Textures are 64 × 64 arrays of 4-bit palette indices (JS). Before a span is drawn, its 16-colour palette is copied into Hn. A tint flag rewrites those 16 entries towards red before drawing, so a whole wall or sprite can be recoloured without touching the framebuffer.

Sprites are segments too: HJ and AA$

Sprites don’t get a renderer of their own. HJ transforms the sprite’s position, pulls it 16 units towards the camera, and builds a two-vertex segment straddling it in view space: a billboard. That segment goes through the same Qy clip/project path as a wall. Some decorations are flagged to stay locked to a world axis instead (flags 0x80000–0x400000). They are built in world space and passed to NR, so they behave like thin walls.

Segments flagged masked (g4 & 2) go to AA$. Its column loop matches AAP, but instead of one strip per column it reads run-length posts from stexels data, each a start row and a length, terminated by 127. It draws only the opaque runs. It reads G6 to hide behind walls but never writes it. Because JT already inserted sprites into Iw sorted far to near, overlapping sprites resolve by painter’s order. That is the same split Wolfenstein uses: a depth array for walls, sorting for sprites.

5.5 How TeaVM rendered the Java

The renderer is plain integer and fixed-point Java, and TeaVM translates it closely. What shows up in the JavaScript is mostly Java’s numeric semantics being enforced by hand:

int and short arithmetic

  • Every int add or subtract is followed by | 0 to force 32-bit wraparound.
  • int × int goes through N = Math.imul. A plain * on doubles would lose the low bits that 16.16 maths depends on.
  • (short) casts become << 16 >> 16. Unsigned byte reads become & 255.

long arithmetic becomes BigInt

  • Java long maps to BigInt: F widens, Cu/Cy multiply/divide, CQ shifts, BI narrows to int, Nu takes the high word.
  • The renderer uses long to keep precision in projection, clipping and the per-column texture coordinate. So LQ, Ic and one line of the AAP loop allocate BigInts every frame, once per column. It is the costliest translation in the hot path, and it is still fast enough for a 176-pixel-wide view.

Arrays and objects

  • Java arrays are wrappers around typed arrays, hence G6.data[n], Et.data[b].
  • System.arraycopy (E2) bounds-checks, then uses TypedArray.set(subarray(...)). That is how floor and ceiling rows are blitted.
  • Fields are renamed too: segment vertices are g1/g0, and a vertex is gS, gT, g3 (x/depth, y/screen-x, texture u).

Control flow

  • Each static method begins with J(), the class-initialiser guard. On first call it runs the renderer class’s <clinit> and then replaces itself with a no-op.
  • The renderer never blocks, so TeaVM emits ordinary functions. None of the $p resume-state machinery from section 10 appears here, and JT is ordinary JS recursion.
  • Register allocation reuses locals freely. In OE’s unrolled loop, b and c swap roles between dst index and tex coord halfway through, and swap back by the end of each pass.

Evidence: functions named above in the inline TeaVM script of index.html. Locate them via the string-pool entries "/sintable.bin", "nd:%1/%2", "li:%1/%2/%3", "/wtexels.bin", "/stexels.bin". sintable.bin decodes to 256 little-endian ints, sin(2πi/256)·65536.

7. Audio in depth: MIDI parsing, synthesis, scheduling, and PCM output

The engine’s media implementation is compact but technically rich. It implements just enough of the J2ME media surface for Doom RPG: load a MIDI stream, realize/prefetch conceptually, set loop count and volume, start/stop, and query running state. The actual synthesis is handwritten Web Audio code.

Important scope: there is no separate WAV/PCM/MP3/OGG asset decoder in the attached engine. All packaged game audio resources are MIDI. The explicit PCM-like data is the generated white-noise buffer for percussion; the browser’s AudioContext then mixes all oscillator/noise nodes into its own sample stream for the audio device.

7.1 MIDI file ingestion

Java opens .mid as a resource stream

The resource shim resolves the path from the embedded resource dictionary. The media shim copies the stream into a Java byte array and passes those bytes to __midiLoad.

Standard MIDI header and tracks are parsed

parseMidi recognizes MThd, reads header length, track count and division, then walks MTrk chunks. Variable-length quantities decode delta times.

Running status is supported

If an event byte does not carry the high status bit, the previous MIDI status byte is reused, matching normal SMF encoding.

Only the events needed by this game are retained

Tempo meta-event FF 51, program change, note-on and note-off are collected. SysEx data is skipped. Note-on with velocity 0 becomes note-off.

Ticks become absolute seconds

Events are sorted by tick. The parser integrates elapsed ticks against the current microseconds-per-quarter-note tempo and MIDI division. Every note becomes a compact structure containing start time, duration, channel, note number, normalized velocity and program.

seconds += (eventTick - lastTick) * tempoUSPerQuarter / 1_000_000 / division
frequency = 440 * 2 ** ((midiNote - 69) / 12)

7.2 Instrument synthesis

There is no SoundFont, sample bank or General MIDI ROM. Program numbers are quantized into a tiny waveform palette:

Program rangeOscillatorInterpretation
0–7TriangleSoft/fundamental-rich approximation
8–31SquareHollow/brassy/reedy approximation
32–39TriangleAnother soft group
40–55SawtoothBright/string-like approximation
56–79SquareBrass/reed-style bucket
80–95SawtoothBright synth-style bucket

Each pitched note creates an OscillatorNode. Frequency uses equal temperament around A4=440 Hz. Velocity is normalized to 0..1, multiplied by 0.22, and non-triangle oscillators receive a further ×0.55 attenuation to stop their stronger harmonic content from dominating.

7.3 Percussion synthesis = generated PCM noise + filtering

MIDI channel 10 (zero-based channel 9) takes a completely different path. The engine lazily allocates a mono AudioBuffer containing half a second of random floating-point samples in [-1,+1] at the current device sample rate. This is actual PCM-like sample data, generated procedurally rather than loaded from the game.

noiseBuf = audioContext.createBuffer(1, sampleRate * 0.5, sampleRate)
for each float sample:
    sample = random() * 2 - 1

A BufferSourceNode replays the noise through a band-pass biquad. The MIDI note number selects a crude drum spectral region: below 40 → 180 Hz, below 50 → 900 Hz, otherwise 5 kHz. Low drums get about 180 ms; others about 90 ms; percussion velocity is boosted ×1.8. This gives kick/snare/hat-like differentiation with almost no asset footprint.

7.4 Envelopes, mixing, volume, looping

Every note has its own GainNode. The envelope is a short linear attack (~6 ms), a sustain plateau, and a ~30 ms linear release. Notes are capped at 4 seconds. Their gains feed a per-player gain; each player gain feeds the global master gain; the master gain feeds AudioContext.destination.

Looping is implemented above the audio graph. A pass schedules the entire song from a chosen absolute AudioContext.currentTime plus 30 ms. The next pass is armed by setTimeout roughly 250 ms before the scheduled end, reducing gaps while avoiding an indefinitely large pre-scheduled graph. A negative loop count means infinite looping; positive counts decrement per pass.

The first key/touch interaction calls audio(), which creates/resumes the AudioContext. This is a practical browser-autoplay adaptation: sound activation occurs under a user gesture before Java-side playback requests need it.

8. RecordStore: J2ME records serialized into localStorage

The Record Management System is emulated rather than replaced by ad-hoc game saves. The Java-side RecordStore shim keeps the familiar concepts: named stores, monotonically allocated record IDs, add/update/read/delete behavior, enumeration, and the expected MIDP exception types.

At the host boundary, each store becomes one string value under a namespaced browser key:

doomrpg:rs:<store-name> → serialized RecordStore

The serialization is compact text. The first field is the next record ID; subsequent records are separated by |; each record is encoded as id=HEXBYTES. On load, the shim splits the string, parses record IDs, converts each pair of hex digits back to a signed byte, and rebuilds the in-memory record arrays. On any mutation it reserializes the store and calls the host setter.

If browser storage throws (for example because storage is unavailable), the host helpers fall back to window.__mem. That preserves runtime behavior for the session but loses persistence after reload.

9. Resource packaging and Java resource streams

All game resources are embedded directly in the HTML as base64 strings. Before the game boots, a small host initializer decodes every string with atob and copies it into a Uint8Array, building window.__res. The base64 dictionary is then deleted.

Observed payload mix

The important architectural detail is that the browser never performs network fetches for game data after the HTML arrives.

The generated resource loader normalizes a leading slash, asks the host for byte length, allocates a Java byte array, asks the host to copy bytes into it, then wraps that data in a stream. This preserves the Class.getResourceAsStream-style consumption model used by the original code.

10. Threads and timing: cooperative Java semantics on the browser event loop

TeaVM compiles blocking Java operations into coroutine-like state machines. The generated functions have explicit resume states, save local variables before suspension, and use callbacks/timers to resume later. Thread.sleep-style behavior becomes setTimeout, not a blocking browser thread.

The input worker illustrates this cleanly: it drains queued keycodes, dispatches them to the active Canvas, then sleeps; TeaVM suspends the Java thread and schedules a future continuation. The browser event loop remains responsive while the Java source retains a threaded programming model.

DOM events enqueue keys, timers resume TeaVM threads, MIDI nodes run on the Web Audio timeline, and RecordStore calls persist browser-side state.

Why this architecture works well

  • Small compatibility surface: most complexity stays in compiled Java, so host code remains inspectable.
  • Portable rendering: software pixels make game output independent of browser drawing semantics.
  • Offline-friendly: all resources live inside one HTML document.
  • Preserved save model: game code still talks in RecordStore terms.
  • Autoplay-safe audio: user input initializes AudioContext early.
  • Deterministic MIDI timing: notes are scheduled on the AudioContext timeline rather than fired by JS timers one by one.
  • Cheap percussion: one reusable half-second noise buffer serves every drum note.
  • Pragmatic timbre: a handful of oscillator shapes provides recognizable music at almost zero sample cost.
